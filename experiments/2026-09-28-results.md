# Background worker experiment — September 28, 2026

Private prototype on top of MIT candidate `8c4889a25acd05b1bfc7e4360854a063c6641f7b`.
The maintainer authorized replacing the connected UNO R4's sketch and confirmed
D2/D3 buttons and D12/D13 LED outputs are a safe test rig. No EEPROM credentials
were saved or changed. The final uploaded image identifies itself as
`0.3.0-background.1`; it was subsequently replaced by the matrix-visualization build below.

## Actual UNO observations

Board: Arduino UNO R4 WiFi, Renesas core 1.5.3. Dependencies: ArduinoJson 7.4.3,
ArduinoMqttClient 0.1.8. Prototype network stack 2048 bytes, core sketch stack
4096 bytes. Worker priority 3, sketch priority 4, one-tick pause in SDK poll.

Both normal and stack-instrumented uploads completed. A setup-status request
reported Wi-Fi disconnected, Room Connector disconnected and no paired Device.
I sent a `join-network` request for a deliberately nonexistent synthetic SSID;
no save/provision request followed. The real WiFiS3 connection attempt timed out
with `network_failed`. Local loop sampling continued throughout.

Representative serial diagnostics from the final measured image:

```text
ED bench loops=30014 maxGapMs=1 rtosFree=368 workerStackMinBytes=336 sketchStackMinBytes=3984
[synthetic join-network request]
[response: network_failed]
ED bench loops=46423 maxGapMs=1 rtosFree=368 workerStackMinBytes=336 sketchStackMinBytes=3984
ED bench loops=51423 maxGapMs=1 rtosFree=368 workerStackMinBytes=336 sketchStackMinBytes=3984
```

The measured maximum loop gap is in millisecond resolution, not a submillisecond
latency guarantee. No physical button press or external output timing was
observed. This is evidence that the real Wi-Fi wait did not stall this sketch,
not full Room Connector/puzzle integration qualification.

The instrumented image uses 136,796 bytes flash and 22,576 bytes static RAM,
leaving 10,192 bytes outside static allocations. This remainder is not measured
available runtime heap. Only 368 bytes remain in the separate RTOS allocation
pool, and the networking task reached 336 bytes of unused reserved stack on the
paths exercised. The normal sketch stack had 3,984 bytes unused. Full-certificate
provisioning and TLS/MQTT paths were not exercised; stack/heap headroom is an
open blocker to making this the default UNO implementation.

Uploaded binary SHA-256:
`e456e9fc45d8b50cbe6bd2a0985dc9d7d7e767f744421defa6df2a6f7f4823a0`.


## Other checks

- Existing description/header validation, 13 JavaScript tests and five C++ suites pass.
- Prototype description/header validation passes.
- Background mailbox tests pass: 200,000 event transfers, 10,000 request handoffs,
  saturation, deadline wrap and stale/expired command rejection. In the simulated
  300 ms busy worker stall, local processing continued and a 50 ms output deadline
  was serviced at 50 ms. This is a host simulation, not physical output timing.
- The same mailbox test passes ThreadSanitizer with no reported races.
- Original example still compiles: UNO 127,388 flash / 13,220 static RAM;
  GIGA 481,412 flash / 79,112 static RAM.
- Final prototype compiles for GIGA: 482,692 flash / 80,008 static RAM. No GIGA
  was connected or uploaded, so its scheduling is not physically qualified.

## Built-in matrix follow-up

At the maintainer's request, uploaded `0.3.0-background.2` with no external LED
requirement: hold D2 for the left matrix block; three D3 presses latch the right
block. Board Reset clears the latch. Stable prop IDs and behavior remain intact;
the two input pins are swapped relative to the earlier prototype. GIGA displays
held D2 in blue and latched D3 in red. Both board compilations and prototype
description/header validation pass. Actual button/visual observations remain
for the maintainer to confirm. The matrix library owns its refresh timer; puzzle
logic still runs in the ordinary loop.

UNO build: 137,676 flash / 22,696 static RAM. GIGA: 482,764 flash / 80,016 static RAM.
